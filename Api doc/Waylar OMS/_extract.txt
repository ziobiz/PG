Create a Buyback Order
A buyback order (order_type: "buy") is the shop buying an item back from a customer — the customer
is the seller, the shop pays. Unlike a regular ("sale") order, money flows out of the shop to the
customer, only after someone verifies (approves) it — it's never paid out the moment the order is created.
The money leaves through whichever route Waylar has configured — not something a partner needs to
know or integrate against. Only one thing follows from it: the customer's recipient details must be complete
(see point 1 below).
===== PAGE 18 =====
Before creating this order, you need:
1. The customer (customer_id) must already have a receiving bank account set via PATCH
/customers/{id} — bank_account_no and (bank_account_name or given_name+surname)
must both be filled in. An email should always be set too — some payout routes require it, and the
order cannot be created without it. (The customer's 13-digit tax_id is required too, and
address_street+ address_city — the tax id only on some payout routes, the address on all of
them.)
2. Enough balance in the outbound wallet (order total × 1.002 — see the fee note below). This isn't
checked at order-creation time, only at verify time (next step). Only Waylar staff can top up this wallet —
there's no endpoint for a partner to do it themselves.
3. If the shop's payout route is INET, the shop (org) must have its own tax id set under Settings > Payout
in OMS beforehand (once, not per customer — no endpoint for a partner to set this; contact Waylar if it
isn't set yet).

estimated_payout_at (v1.21.0) — roughly when the money actually goes out. null when decision:
"reject" (nothing was paid out). On "approve":
Paid via INET — a real, precise time: the next tick of IC-TWS's batch clock, which runs every 5 minutes
on the wall clock (13:05, 13:10, 13:15, ...) — not "5 minutes after this call". A voucher accepted at 13:07
still waits for 13:10, whatever time it was actually accepted at.
Paid via Xendit — just Waylar's own rough estimate (~30 min), not a confirmed SLA from Xendit —
Xendit publishes no fixed batch clock the way IC-TWS does.
Paid via MANA (v1.27.0) — usually settles during this very call; if not, Waylar re-checks its status every
5 minutes, so this is a ~10 min estimate, not an SLA. At most ฿ 50,000 per order — above that you get
an error and the order stays "pending" (nothing was debited).
Whatever the rail, the order.buy_payout_succeeded / order.buy_payout_failed webhook can
arrive before this call's response (the payout confirms faster than the response returns). Treat the
webhook, or GET /orders/{code}, as the source of truth — never let this response overwrite a status a
webhook already gave you.
decision:
"approve" — checks whether the outbound wallet can cover the order (order total × 1.002); if so,
sends the payout to the customer's bank account on file immediately. buy_verify_status becomes
"verified" and buy_payout_status becomes "sent" — which is not yet money in their
account: the provider has only accepted the request and can still refuse it afterwards. The order
becomes "Received" (stock added) only once the provider confirms the transfer
(buy_payout_status: "paid"). If it is refused later, buy_verify_status goes back to "pending"
with buy_payout_status: "failed", the amount is returned to the wallet automatically, and the
order can simply be verified again. — safe to retry if the previous call returned an insufficient-
balance error (nothing was debited or touched on that failure). Do not retry if buy_verify_status
comes back as "unknown" — that means the provider's result was unclear (timeout/5xx) and the
money may genuinely have already gone out; wait for Waylar to check with the provider first.
"reject" — cancels the order (status: "Cancelled"), reversing stock if any had already been
received. No money moves. buy_verify_status becomes "rejected".

Resolve a Payer Review
POST /api/v1/orders/{code}/payer-review
When transfer.review_status is "pending" (money arrived, but the payer's name doesn't match the
order's customer — see Check Payment Status), this lets the partner decide directly via the API instead of
going into the OMS dashboard — the partner usually knows best whether the payer really is their customer.
Headers
Header Value
X-API-Key wlr_<key> (required)
Content-Type application/json
Body
Field Type Required Description
decision string ✅ "approve" or "reject"
note string Note (kept in the order's event log)
reviewed_by string Reviewer's name/email (defaults to"api" if omitted)
decision means one of two different things depending on the situation (the server figures out which from
the order itself):
Ordinary payer-name mismatch — approve = it is the same person, pay the merchant normally
(schedules a settlement). reject = it isn't, holds the payout for a human to sort out.
Money arrived after the order was already cancelled — approve = keep the money, pay the
merchant normally (the order stays Cancelled — stock already released is not restored). reject =
confirm the money should not be kept — a refund to the customer is needed instead.
Both situations return the exact same response/webhook shape — the example below is the mismatch
case; "money after cancellation" gets an identical response (payer_review_status/ review_status use
the same values in both cases, there's no special value for this one).

curl -X POST https://oms.waylar.net/api/v1/orders/SO-12345678/payer-review \
  -H "X-API-Key: wlr_abc123..." \
  -H "Content-Type: application/json" \
  -d '{ "decision": "approve", "reviewed_by": "staff@merchant.com" }'

{ "ok": true, "order_code": "SO-12345678", "payer_review_status": "approved", 
"reviewed_at": "2026-09-14T10:00:00.000Z" }
Response 200 (reject)
{ "ok": true, "order_code": "SO-12345678", "payer_review_status": "rejected", 
"reviewed_at": "2026-09-14T10:00:00.000Z" }
approve fires both order.paid and order.payer_review_resolved — order.paid was never sent
while the review was pending (the system guarantees this ordering; there is no path where order.paid
could already have gone out before a review starts). reject fires only order.payer_review_resolved
— no order.paid follows. See Outbound webhooks.
What happens after reject: closes the review as "rejected", and the system now automatically
opens a support ticket for Waylar's own Support team (v1.11.0) so they process the customer refund —
this doesn't touch this API's contract at all (no new field/response/ webhook for partners), it's purely an
internal Waylar mechanism. There is still no refund endpoint or webhook exposed to partners anywhere in
this API, and no webhook fires when the refund is actually completed — there is no formal partner-facing
refund flow yet.
Orders with no customer_id: the payer-name review needs a customer to compare against — if the order
has no customer_id at all (an org that doesn't require it), this check is skipped entirely (never held, no
matter what name it was paid under). transfer.review_status will always be "" for such an order — it
can never show "pending".

Notes
An API key is scoped to one org — products can only be created in the org that issued the key.
SKUs must be unique per org across the whole system (not just per key).
margin in responses is computed as (price - cost) / price * 100 (%).
Outbound webhooks
Set the URL and secret per org under OMS → Settings → Webhook — one tab per destination: the "Order
paid" tab covers all order.*/wallet_topup.* events, the "Support Ticket" tab covers only
support_ticket.status_changed (v1.20.0). They can point at two different URLs/secrets, or the same
one — your choice. Every request is signed with an HMAC-SHA256 of the raw JSON body (before parsing)
using that tab's own secret, encoded as hex, sent as x-waylar-signature.
Timestamp/nonce: none — the payload carries no replay-protection field of any kind.
Retry: best-effort, up to 2 attempts total (1 initial + 1 retry). No further retries, no durable queue — if a
partner endpoint is down or slow for both attempts, that event is lost.
Expected response: any HTTP 2xx is treated as success; anything else is a failure (retried if a retry is
still available). The response body is never inspected.
Idempotency: no idempotency key is sent — dedupe on your side if needed (e.g. a so+event pair
against events you've already processed).
Order (order.*, wallet_topup.*) — configured on the "Order paid" tab

so — the order code (same as code in POST /orders's response)
