API Reference · Online payments

Accept payments from your own checkout and confirm every result by webhook

This reference covers the full online payment path: authenticate, create a charge, let your customer pay, receive the result, and refund when needed. Every endpoint is JSON over HTTPS.

What this version covers

You build your own checkout and create each payment with the Charges API. We process the payment, handle any redirect or QR step, and send you a webhook with the result. Refunds, events and reporting work the same way for every payment method.

Hosted payment pages are not part of this release. Every card payment therefore runs through your own checkout, which affects your PCI DSS scope — see Security & compliance.

Getting started

Authentication

Authenticate every request with HTTP Basic Auth. Use your accountId as the username and the key for the call as the password. Requests without credentials, or sent over plain HTTP, are rejected.

KeyFormatWhere to use it
Secret keysk_live_…
sk_test_…		Your server only. Works with every endpoint under /v1.
Publishable keypk_live_…
pk_test_…		Browsers and mobile apps. Works only with /client/v1 endpoints (card tokens).
Platform keyplk_live_…
plk_test_…		Platforms that manage payments for several sub-merchants. Send with the GW-Platform-Id header.

Sandbox and live keys are separate and cannot be used across environments. Check the _test_ or _live_ prefix, or the livemode field on any response.

Acting on behalf of a sub-merchant

Use the sub-merchant's accountId as the username, your platform key as the password, and your platform ID in GW-Platform-Id. Everything the request creates belongs to that sub-merchant's account.

Keep secret and platform keys out of front-end code, mobile app bundles and source control. If a key is exposed, rotate it immediately under Developers → API keys. You choose how long the old key keeps working.

Getting started

Safe retries with idempotency keys

Networks fail. Send an Idempotency-Key header on every POST that moves money or creates a payment — charges and refunds — so a retry never charges or refunds your customer twice.

  • Use a UUID v4, or any random string up to 255 characters, tied to your own order.
  • Keys are kept for 24 hours. A repeat with the same key and body returns the original response with Idempotent-Replayed: true.
  • Same key, different body → 409 idempotency_conflict.
  • Same key while the first request is still running → 409 request_in_progress. Wait, then retry.
  • GET requests don't need a key.
Retry only on timeouts, 5xx responses, 409 request_in_progress and 429. Always reuse the same key, and back off exponentially with jitter.
Request
POST /v1/charges
Idempotency-Key: 4f0d6a8e-2b1c-4c55-9a0e-7d3f18b2c901
Replayed response
HTTP/1.1 201 Created
Idempotent-Replayed: true
GW-Request-Id: req_01J8ZQ6N2C

Errors & rate limits

A 2xx response means we accepted your request — not that the payment succeeded. A declined card still returns 2xx, with the reason in failure. A 4xx or 5xx response means the request itself was rejected, and always carries an error object.

HTTPcodeMeaning and what to do
400invalid_jsonThe body isn't valid JSON.
400validation_failedA value is missing or invalid. param names the field.
401authentication_failedCredentials are missing, or the key doesn't match the account or environment.
403permission_deniedThis key isn't allowed to perform the action.
403account_restrictedYour account, or this payment method, isn't enabled. Contact support.
404not_foundThe object doesn't exist, or belongs to the other environment.
409idempotency_conflictThe idempotency key was reused with a different body.
409request_in_progressAn identical request is still processing. Retry shortly.
422invalid_stateThe object can't do this in its current state — for example, refunding a pending charge.
422refund_in_progressA refund on this charge is still processing. Wait for its webhook.
422insufficient_balanceYour balance can't cover this refund.
429rate_limitedToo many requests. Wait for Retry-After.
500internal_errorSomething failed on our side. Retry with the same idempotency key.
503provider_unavailableThe bank or wallet is temporarily unavailable. Retry, or offer another payment method.

Rate limits

Every response includes RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset. The most common cause of 429 is polling for payment status too often — use webhooks instead.

Security & compliance

How you integrate decides how much of the card-data security work (PCI DSS) falls on you. Card data is processed in our environment, and your page never has to send it to your own server — but because your page collects it, your integration is assessed accordingly.

IntegrationCard data on your systems?Typical PCI DSS questionnaire
Your own card form calling /client/v1/tokensEntered on your page, sent straight to usSAQ A-EP
PromptPay, mobile banking, e-walletsNo card data involved—

Your acquirer or a Qualified Security Assessor (QSA) makes the final call on which questionnaire applies to you. Plan for SAQ A-EP if you take cards in this release: it adds requirements for your payment page, including script controls and change detection. A hosted payment page, which keeps card integrations in SAQ A, is planned for a later release.

Our compliance status: We are not yet PCI DSS certified as a service provider; certification is in progress. You can request our Attestation of Compliance (AOC), once issued, from compliance@gateway.example.
  • Every API call uses TLS 1.2 or higher.
  • Payment pages send X-Frame-Options: DENY, so they can't be embedded in an iframe.
  • Never log, store or email full card numbers or security codes.

Charges

How charges work

A charge is one attempt to pay, created by your call to POST /v1/charges. Every payment becomes a charge, and the origin field records where it came from — api in this release.

pending→succeeded|failed|expired

succeeded, failed and expired are final. A failed charge can't be retried, so create a new one. Refunds don't change a charge's status; they increase amountRefunded.

transactionTime is set once, the moment a charge first reaches a final status, and never changes after that — use it to know when the payment was actually settled. updatedAt is different: it also moves whenever you PATCH metadata, so it can't tell you when a charge became final.

Abandoned payments can stay pending for a long time — for example when a customer closes the QR screen or never opens their banking app. Set expiresAt when you create the charge, or call expire when your order times out. Never wait on a final status without a timeout of your own.

    F->>S: Sends the order (and card token for cards)

Refunds

Create a refund

POST/v1/charges/{chargeId}/refundssecret key

Returns money from a succeeded charge. The refund starts as pending, and the webhook tells you the result.

FieldDescription
amountintegerIn satang. Leave it out to refund everything still refundable (amount − amountRefunded). 0 is rejected.
reasonenumrequested_by_customer duplicate fraudulent other
notestring ≤ 500Your internal note.
metadataobjectSee Conventions.

Rules

  • The charge must be succeeded.
  • Refundable methods: card, card_installment, promptpay, and ewallet payments made with alipay or wechatpay.
  • Partial refunds work only on card. Other methods must be refunded in full.
  • One refund at a time per charge. Another one while the first is pending returns 422 refund_in_progress.
  • Refunds are paid from your balance. If it isn't enough, you get 422 insufficient_balance.

Status

pending→succeeded|failed
succeeded means the payment provider has accepted the refund, not that your customer has the money yet. How long it takes depends on your customer's bank or wallet. Tell your customer the refund is on its way.

transactionTime is set once the refund first reaches succeeded or failed, and never changes after that — same idea as charges.

Receiving events

Add your endpoint under Developers → Webhooks. We send a POST as soon as a payment reaches its final state. Fulfil orders from the webhook — it arrives even if your customer closes the browser, which returnUrl can't guarantee.

typeSent when
charge.succeededA payment succeeds.
charge.failedA payment fails. Includes failure.
charge.expiredA payment times out or you expire it.
refund.succeededThe payment provider accepts a refund.

Responding and retries

  • Return a 2xx within 10 seconds. Do any heavy work asynchronously after responding.
  • Any other response, or a timeout, is retried up to 10 times with exponential backoff.
  • An event may arrive more than once, and out of order. Deduplicate by event id, and check data.object.status before you update an order.
  • If every attempt fails, fetch missed events from the Events API.

Webhooks

Verifying signatures

Every webhook carries a GW-Signature header in the form t=<unix seconds>,v1=<hex>. Verify it before you trust the payload.

  1. Read t and every v1 value from the header. While you rotate your secret, there can be more than one v1.
  2. Build the string {t}.{rawBody} from the body exactly as you received it. Don't parse and re-serialize it.
  3. Compute an HMAC-SHA256 with your endpoint's signing secret (whsec_…) and hex-encode it.
  4. Compare it with each v1 in constant time. One match is enough.
  5. Reject the request if t is more than 5 minutes from your current time. This blocks replayed webhooks.
Node.js · Express
import crypto from "node:crypto";
import express from "express";

const SECRET = process.env.GW_WEBHOOK_SECRET; // whsec_…
const TOLERANCE = 300;

function verify(header, rawBody) {
  const parts = header.split(",").map(p => p.split("="));
  const t = parts.find(([k]) => k === "t")?.[1];
  const sigs = parts.filter(([k]) => k === "v1").map(([, v]) => v);
  if (!t || !sigs.length) return false;
  if (Math.abs(Date.now() / 1000 - Number(t)) > TOLERANCE) return false;

  const expected = crypto.createHmac("sha256", SECRET)
    .update(`${t}.${rawBody}`).digest();
  return sigs.some(s => {
    const got = Buffer.from(s, "hex");
    return got.length === expected.length
      && crypto.timingSafeEqual(got, expected);
  });
}

const app = express();
app.post("/hooks/gateway",
  express.raw({ type: "application/json" }),
  (req, res) => {
    if (!verify(req.get("GW-Signature") ?? "", req.body.toString("utf8")))
      return res.sendStatus(400);
    const event = JSON.parse(req.body);
    res.sendStatus(200);            // respond first
    queue.push(event);              // dedupe by event.id in the worker
  });

The sandbox accepts the same requests as live, but no real money moves. Use your _test_ keys with sandbox.api.gateway.example.
