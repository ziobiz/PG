Related: 
Unified checkout flow
 ·

1. Scope

  
  
Add 
crypto
 payments on the same merchant MID that already uses card checkout.
    Shopper and merchant UI always show 
ICOPAY
 only (no PG brand).

  

Recommended:
 same unified prepare as cards, with
    
payMeans=CRYPTO
. Reuse the existing NOTI Callback/Result used for cards (e.g. ElementPay).

  
2. Prerequisites (HQ must enable)

  
  

    

Item

Note

    

Merchant crypto use = Y

Company detail or HQ Policy → Pay·URL → Crypto settings

    

Allowed assets

e.g. USDT only for first go-live

    

Merchant receive wallet

One network + address per enabled asset (settlement payout)

    

HQ custody wallet

ICOPAY deposit address for that asset×network

    

Company use = Y

Unused / permanent stop blocks crypto

  

  
3. Prepare (recommended)

  
  

POST {publicApiBaseUrl}/api/middleware/v1/merchant/checkout/prepare

  
Header: 
Content-Type: application/json
, 
X-Icopay-Merchant-Broker-Secret
 (same live secret as cards).

  
{
  "compId": "6000000064",
  "orderNo": "ORD-CRYPTO-001",
  "amount": "10000",
  "displayCurrency": "JPY",
  "payMeans": "CRYPTO",
  "productName": "Sample product",
  "lang": "ENG",
  "buyer": {
    "email": "buyer@example.com",
    "phone": "1012345678",
    "countryIso2": "KR",
    "firstName": "Gildong",
    "lastName": "Hong"
  }
}

  

    

Field

Required

Description

    

payMeans

M*

CRYPTO
 (aliases: checkoutMeans / paymentMeans)

    

amount

M

Display amount; ICOPAY quotes to USD then remittance asset

    

displayCurrency

O

JPY/USD/… — merchant crypto display currency if omitted

    

assetCode / networkCode

O

Optional; shopper can pick on ICOPAY crypto page

    

buyer name/email

M*

Latin letters for name/email; phone digits (same as crypto UI)

  

  

Response:
 
pgVendor
 always 
ICOPAY
. Use 
payUrl
 / 
sessionToken
.
    Crypto session tokens may start with 
cr_
.

  
Alternative: 
POST /api/pay/crypto/prepare
 with 
compId
 (same product rules).

5. Callback / Result

  
  
Do 
not
 register a separate crypto Callback on ICOPAY company “Payment notify URL”.
    Flow: deposit confirm → ICOPAY → 
POST /noti/crypto
 → NOTI relays to the 
same merchant callbackUrl
 as cards (match by Comp-Id).

  
Extend your existing webhook handler:

  

    
Match order via 
orderid
 / 
orderNo

    
Idempotent success handling (
returncode
 / JPAY-compatible schema)

    
Extra fields: 
assetCode
, 
networkCode
, 
depositTxHash

    
Branch when 
pgKind
/
van
 indicates crypto

  

  
Status poll: 
GET .../merchant/checkout/status?compId=&amp;orderNo=
 or
    
GET /api/pay/crypto/status
.
