1. 이 메뉴얼의 범위

결제 확정 후 가맹 서버로 오는 백그라운드 통보(웹훅)와, 웹훅 서명(HMAC)을 켜었을 때의 검증 방법을 설명합니다.

  • 브라우저 Result URL 리다이렉트와는 별개입니다.
  • 결제대행사(PG) 이름·operationalPgCd는 페이로드에 포함되지 않습니다(ICOPAY 중립).
  • 일상 화면 운영은 「가맹점 운영 메뉴얼」을, Checkout API는 가맹점API·merchant-api-samples를 참고하십시오.

2. 통보 경로 (NOTI / ICOPAY 직통)

경로발신설명
일반(권장 기준)NOTI → 가맹 callbackUrl결제 확정 서버 POST
보조ICOPAY → 결제통보·수신통보 URL직통 POST (서명 ON이면 동일 헤더·시크릿)
서명 활성 시 NOTI·ICOPAY 직통 모두 같은 HMAC 검증을 하면 됩니다. ICOPAY가 NOTI에 설정을 동기합니다.

3. STEP 1 관리자 설정

메뉴: 본사정책 > 결제·URL > 결제 라우팅 > 웹훅 서명
메뉴: 업체관리 > 가맹 상세 > 웹훅 서명
구분메뉴값
본사 기본결제 라우팅 → 웹훅 서명OFF(비활성)가 기본 / ON(활성)
가맹가맹 상세 → 웹훅 서명본사설정 따름 / 활성 / 비활성 (가맹 우선)
  1. 가맹에서 활성을 선택합니다. (본사 기본이 OFF여도 가맹만 ON 가능)
  2. 시크릿 재발급 — 평문은 한 번만 표시됩니다. 가맹 서버 환경변수 등에만 보관합니다.
  3. 채팅·티켓·로그에 시크릿을 남기지 마십시오.
실효가 비활성(N)이면 서명 헤더 없이 POST됩니다. 서명 ON인데 시크릿을 서버에 안 넣으면 검증이 실패합니다.

4. STEP 2 서명 규격

항목내용
헤더X-Icopay-Signature: v1={hex}
알고리즘HMAC-SHA256
메시지raw HTTP body (수신 바이트 그대로 — 파싱 후 재직렬화 금지)
키웹훅 서명 시크릿 (재발급 시 받은 값)
hex대소문자 무시 비교 권장
실패 응답HTTP 401 권장 · 성공 200
expected = HMAC_SHA256_HEX(raw_body, webhook_secret)
header   = "v1=" + expected

5. STEP 3 가맹 서버 구현

  • HTTPS 엔드포인트
  • 타임아웃 내 HTTP 200 (검증 성공 시)
  • 동일 주문 중복 통보를 가정한 멱등 처리
  • 서명 활성 시: raw body로 HMAC 검증 후 JSON 파싱
  • 환경변수 예: ICOPAY_WEBHOOK_SIGN_SECRET
페이로드 예 필드: event, compId, trnId, orderNo, status, paymentStatus, amount, currency, paidAt, notifyChannel, ts 등

8. 체크리스트

  1. 가맹 웹훅 서명 = 활성 (또는 본사 ON + 따름)
  2. 시크릿 재발급 → 서버에만 보관
  3. callbackUrl HTTPS · 멱등
  4. X-Icopay-Signature 검증 · 실패 401
  5. 테스트 결제 후 통보 수신·서명 yes 로그 확인

9. FAQ

본사 기본이 OFF인데 가맹만 켤 수 있나요?
네. 가맹 상세에서 활성하면 본사 OFF여도 서명됩니다.
시크릿을 다시 보고 싶습니다.
평문은 재발급 직후 1회만 보입니다. 분실 시 재발급하고 서버 설정을 교체하세요.
서명이 맞지 않습니다.
raw body를 그대로 쓰는지, 시크릿·헤더 형식(v1=)이 맞는지 확인하세요. JSON을 다시 stringify하면 실패합니다.
Result 페이지에서도 서명하나요?
아니요. 브라우저 Result와 서버 웹훅은 별개입니다.
