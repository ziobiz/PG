1. Ops overview

This document explains, from an operations perspective, which triggers fire and when when each switch under “Risk Filtering” is set to Enabled.

  • Audience: HQ operators · permission screen M0129 (Risk Settings)
  • Policy storage: tb_hq_risk_card_policy (id=1) · applied to all merchants immediately on save
  • Presale block: immediately before calling the PG (JPAY · ChillPay · Eximbay, etc.)
  • Postsale cooldown: after JPAY pay_index for high-risk · PY0124 (independent switches)

2. Risk Settings vs Risk Filtering

AreaTriggerOutcome
Risk Settings (risk management)Same card non-success (FAIL · cancel · void · unpaid, etc.) accumulationStage 1–4 wait · auto-register inactive card
Risk FilteringFormat · velocity · contact mismatch · suspicious name, etc.PG not called · system cancel (20) · Risk Status
Merchant risk statusPer-merchant risk mode (HQ / separate / unused)Shows applied wait time · auto-register values

Merchant “separate / unused” takes precedence for risk management (accumulation triggers). Presale filter switches follow HQ policy.

3. End-to-end flow

Buyer payment attempt → (other checks: card brand · policy, etc.) → If 【Presale filter Enabled=Y】, run item checks (§5 order) → On violation: PG not called · cancel (20) · Risk Status · buyer message → On pass: PG approval request → (JPAY only) Postsale high-risk / PY0124 → cooldown · status (when those switches=Y)
Hosted flow (no card number collected): email · phone · name · IP · email velocity are primary. Without a card hash, card velocity and contact mismatch are effectively skipped.

5. Presale filter check order

When Presale filter Enabled=Y, the code evaluates in the order below and stops at the first violation.

  1. Invalid email — EMAIL_INVALID
  2. Invalid phone — PHONE_INVALID
  3. Suspicious holder name — HOLDER_NAME_SUSPICIOUS
  4. Card velocity limit — VELOCITY_CARD
  5. Email velocity limit — VELOCITY_EMAIL
  6. IP velocity limit — VELOCITY_IP
  7. Buyer contact mismatch — BUYER_*_MISMATCH (email → phone → name)
① EMAIL_INVALID → ② PHONE_INVALID → ③ HOLDER_NAME_SUSPICIOUS → ④ VELOCITY_CARD → ⑤ VELOCITY_EMAIL → ⑥ VELOCITY_IP → ⑦ BUYER_EMAIL / PHONE / NAME_MISMATCH
If an individual switch is Disabled, only that step is skipped. Example: email format OFF → skip ①, then continue from ②.

6. Block outcomes · Ops verification

  1. No approval request is sent to the PG
  2. One attempt is recorded in the system with status cancel (20)
  3. Written to tb_pay_risk_filter_event → Ops Management → Risk Status
  4. Buyer response: multilingual message · error code PRESALE_RISK_FILTER

If a legitimate customer is blocked, check filterCode on the status screen, then ease only that item (Disabled) or adjust the velocity window / count.
