# UI 기반 개발 방향 및 연동 분석

> 질문: "이 UI를 바탕으로 앞으로 어떻게 개발할 예정인가? 준 소스를 바탕으로 UI만 경해서 연동하는가? 매우 다른 기능도 있을 것 같은데 분석해 달라."

---

## 1. 현재 상태 요약

| 구분 | 내용 |
|------|------|
| **프론트(UI)** | `site/` — fxhj·참고 이미지 기반으로 **메뉴·레이아웃·화면 껍데기**까지 구현됨 |
| **화면 단위** | 23개 메뉴별로 **검색 폼·요약·버튼·그리드·페이지네이션** HTML만 생성, **실제 데이터 조회/저장 없음** |
| **참고 소스** | fxhj 저장 HTML, `layout/left-side-menu.html`, 기존 PG 소스(Spring/JSP/Oracle, 2011년경) |
| **백엔드** | `server/server.js` — 정적 서빙 + mock 로그인만 존재, 나머지 API는 스텁 수준 |

즉, **지금은 “UI만 맞춘 상태”**이고, **실제 조회·저장·정산·엑셀·통보 등 기능은 아직 미연동**입니다.

---

## 2. 앞으로 개발 방향: “UI만 경해서 연동”이 아닌 이유

**단순히 “기존 소스에 UI만 갈아끼워 연동”하는 방식은 권장되지 않습니다.**  
이미 `개발방향_기존소스_vs_신규개발_분석.md`에서 정리한 대로:

- **기존 소스**: Spring 2.x, JSP, Resin, Oracle 10g, 이니시스 단일 PG, OTP·보안 미비
- **목표**: 다중 PG, 다국어, 유연한 정산, fxhj 수준 UI·OTP·보안

그래서 **“UI는 지금 만든 것을 바탕으로 두고, 백엔드·도메인은 신규(또는 하이브리드)로 설계한 뒤 연동”**하는 흐름이 맞습니다.

---

## 3. 개발 방향 제안: 3단계

### 3-1. 1단계: UI 고정 + API 계약

- **UI**: 현재 `site/` 구조 유지 (메뉴·탭·화면별 검색/그리드/버튼).
- **할 일**:
  - 메뉴(URL)별로 **어떤 API를 호출할지**만 정리 (예: 공지사항 목록 GET, 결제내역 검색 POST, 정산확정 POST, 엑셀 다운로드 등).
  - `site/js`에서 **검색·저장·엑셀 버튼**에 붙일 **API URL·요청/응답 형식**을 문서로 정의.
- **결과**: “이 UI는 이 API를 쓴다”는 **명세만 확정**. 실제 백엔드는 아직 mock/스텁이어도 됨.

→ **“UI만 경해서 연동”이 아니라 “UI를 기준으로 연동할 API를 먼저 정리”하는 단계.**

---

### 3-2. 2단계: 백엔드 구현 (신규 또는 하이브리드)

- **권장**: `개발방향_기존소스_vs_신규개발_분석.md`의 **옵션 C(하이브리드)**  
  - **기술**: 신규 스택 (예: Spring Boot, REST API, 현대 DB).  
  - **도메인/기능**: 기존 소스·DB·fxhj 화면을 **명세·레퍼런스**로만 참고해, “동작 규칙”을 새로 구현.
- **할 일**:
  - 1단계에서 정한 API를 **실제로 구현** (로그인/OTP, 공지 목록, 결제내역 검색, 정산확정, 엑셀 등).
  - DB·도메인은 기존 테이블/필드 의미를 참고해 **재설계** (이름·관계 유지, 필요 시 확장).
- **결과**: UI가 호출할 **실제 백엔드**가 생김.

→ **기존 소스는 “복붙”이 아니라 “명세서”로만 쓰고, 기능은 새로 만드는 단계.**

---

### 3-3. 3단계: 프론트–백 연동 및 기능 차이 정리

- **할 일**:
  - `site/js`에서 **검색·저장·엑셀·정산확정** 등 버튼에 **실제 API 호출** 연결 (fetch/axios 등).
  - 그리드에 **API 응답 데이터** 바인딩, 페이지네이션·엑셀 다운로드 연동.
  - **기존 소스와 다른 점**을 문서로 정리 (아래 4절 참고).
- **결과**: 지금 UI가 **실제 데이터와 동작**으로 동작.

→ **“UI를 바탕으로” 연동을 완료하고, “매우 다른 기능”이 있으면 명시하는 단계.**

---

## 4. “매우 다른 기능” 있을 수 있는 부분 — 분석

UI(메뉴·화면 구성)는 fxhj·참고와 맞췄지만, **기존 소스·fxhj와 우리가 새로 만드는 시스템이 다를 수 있는 부분**을 정리하면 아래와 같습니다.

| 구분 | 기존 소스 / fxhj | 우리 방향 (권장) | 차이·비고 |
|------|------------------|-------------------|-----------|
| **인증** | ID/PW + 세션 (기존), fxhj는 OTP 등 | OTP·초기비밀번호 변경·세션 정책 등 **신규 설계** | UI는 이미 OTP·초기비번 모달 반영, 백만 구현하면 됨 |
| **PG 연동** | 이니시스 단일, TCP 결제 서버 | **다중 PG·어댑터 구조** 목표 | 기존 코드 “그대로” 붙이기 어렵고, 신규 설계 필요 |
| **정산/과금** | 기존 DB·로직에 맞춤 | **유연한 정산 주기·수수료 정책** 등 재설계 | 도메인 개념은 기존 참고, 로직은 새로 구현 |
| **다국어** | 한글 위주 | **다국어·리소스 번들** 설계 가능 | UI 텍스트를 나중에 키 기반으로 바꾸는 작업 필요 |
| **메뉴/권한** | 기존 메뉴 ID·역할 | **역할별 메뉴 노출·API 권한** 재정의 | URL·메뉴 구조는 유지, “누가 볼 수 있는지”만 새로 정의 |
| **거래/정산 화면** | fxhj는 38컬럼 등 복잡 그리드 | **필수 컬럼 먼저**, 단계적 확장 | UI는 이미 일부 컬럼만 넣은 상태, API 설계 시 필드 추가 가능 |
| **통보·URL 관리** | 기존 방식 | **동일 기능을 REST·이벤트 기반**으로 재구현 가능 | “하는 일”은 같게, “구현 방식”만 다를 수 있음 |

정리하면:

- **UI를 바탕으로 연동**하는 것은 맞고,
- **기존 소스는 “그대로 붙이는 것”이 아니라 “명세·레퍼런스”로만 쓰고**,  
- **실제 기능(인증, PG, 정산, 다국어 등)은 목표에 맞게 새로 설계·구현**하는 쪽이 맞습니다.

---

## 5. 구체적인 다음 단계 제안

1. **API 목록 정리**  
   - 23개 메뉴(화면)별로:  
     - 목록/검색 API (GET/POST, 파라미터),  
     - 저장/수정/삭제 API,  
     - 엑셀 다운로드, 정산확정 등 **액션 API**  
   - 를 한 문서(예: `docs/API_목록_및_요청응답.md`)로 정리.

2. **백엔드 선택**  
   - 하이브리드 권장안대로 **신규 스택** (예: Spring Boot + REST + PostgreSQL 등)으로 1단계 API 구현.  
   - 기존 소스의 **테이블·컬럼·관계**를 참고해 스키마 초안 작성.

3. **프론트 연동**  
   - `site/js/app.js`, `screens.js` 및 각 화면 이벤트에서:  
     - 검색 버튼 → 목록 API 호출 → 그리드 갱신  
     - 저장/정산확정/엑셀 → 해당 API 호출  
   - 로그인/OTP는 이미 UI 있으므로 **백엔드 API만 맞추면** 연동 가능.

4. **차이 문서 유지**  
   - “기존 소스·fxhj와 우리가 다르게 만든 부분”을 위 표처럼 **기능 단위로 문서**에 두고,  
   - 추후 요구가 생기면 “그 부분만 기존 동작에 맞춘다” 같은 선택이 가능하도록 함.

## 6. 요약

| 질문 | 답변 |
|------|------|
| **이 UI를 바탕으로 어떻게 개발할 예정인가?** | ① UI는 유지한 채 **연동할 API를 먼저 정리** → ② **백엔드는 신규(또는 하이브리드)**로 구현 → ③ **프론트에서 해당 API 호출로 연동**하는 3단계로 진행하는 것이 적절합니다. |
| **준 소스를 바탕으로 UI만 경해서 연동하나?** | **아니요.** UI는 “경해서(바꿔서)” 쓰되, **기능·백엔드는 “기존 소스 복붙”이 아니라 “기존 소스는 명세로만 참고하고 새로 구현”**하는 방식이 맞습니다. (이미 `개발방향_기존소스_vs_신규개발_분석.md`에서 하이브리드 권장.) |
| **매우 다른 기능도 있을 것 같은데?** | **있을 수 있습니다.** 인증(OTP)·PG 다중 연동·정산 정책·다국어·권한 등은 **목표에 맞게 새로 설계**하는 부분이고, 위 4절 표처럼 “어디가 같고 어디가 다른지”를 문서로 두고 단계적으로 맞추면 됩니다. |

이 문서는 **UI 기반 개발 방향**과 **“UI만 경해서 연동”이 아닌 이유**, **다른 기능이 있을 수 있는 지점**을 분석한 내용입니다.  
다음 단계로 **API 목록 문서**나 **1단계 API 스펙 초안**을 구체적으로 작성할 수 있습니다.
