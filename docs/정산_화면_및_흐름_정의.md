# 정산 화면·데이터 흐름 (단일 기준)

운영·개발 공통으로 아래를 **단일 진실(single source of truth)** 로 둡니다. 코드 반영: `SettlementCalcService.isMerchantStatementVisibleSettlementRun`, `isDistributedForMerchantStatementView`, `SettlementRun` 상태·`settlement_publish_sts`, `payout_hold_yn`.

## 1. 핵심 엔티티: 정산 실행 (`SettlementRun`)

| 필드·개념 | 의미 |
|-----------|------|
| `status` | `CALCULATED` = 확정(금액·건수 확정). 그 전 단계는 실행·재계산 대상. |
| `settlement_publish_sts` | `PENDING` = 배포 대기(정산배포 큐). `DISTRIBUTED` = 가맹·유통·리포트(AGG/EXE/SUM)에 반영 가능. `HOLD` = 배포 보류(정산대기 큐). **레거시 null/blank 는 DISTRIBUTED 와 동일 취급.** |
| `payout_hold_yn` = `Y` | 지급 보류 — 아래 **모든** “대외·집계” 화면에서 제외. |

## 2. 단계별 흐름 (운영자 관점)

```
결제·거래 집계
    → 정산 실행 생성·확정 (정산구분 AUTO = 배치만 / 비자동 = 배치 제외 시 「수동실행」버튼)
    → settlement_publish_sts = PENDING (정산배포 큐)
        → [정산배포] → DISTRIBUTED → 가맹점정산내역·유통 집계·정산리포트(AGG/EXE/SUM)·상세 API
        → [선택 홀딩] → HOLD → 정산대기 (가맹 정산내역·위 집계 제외)
```

- **정산실행** 목록: **전체 실행 이력** 조회(자동 가맹 행은 선택 불가). **`수동실행` 버튼**은 정산구분 **AUTO 가맹을 제외**하고 비자동만 계산합니다.
- **정산배포 / 정산대기**: `result/list` + `publishTab` 으로 `PENDING` vs `HOLD` 분리.

## 3. 화면별 역할 (12항 정리)

| # | 화면 | 목적 | 포함되는 실행 조건(요약) |
|---|------|------|---------------------------|
| 1 | 통합정산 | 결제·정산 예정일 등 결제 관점 통합 조회 | 결제/통합 도메인 (정산 실행 단계와 별도 층) |
| 2 | 수수료내역 | 거래·정책별 수수료 원장·검증 | 거래/수수료 도메인 |
| 3 | 정산실행 | 이력 조회·비자동 가맹 **`수동실행`**·상세 | 목록은 전체; 버튼 실행은 AUTO 제외·동일 주기 규칙 |
| 4 | 정산배포 | `PENDING` → 배포(DISTRIBUTED) 또는 홀딩(HOLD) | `publishTab=PENDING` |
| 5 | 정산대기 | 홀딩(`HOLD`) 건 관리 | `publishTab=HOLD` |
| 6 | 가맹점정산내역 | 가맹 공개용 확정 정산 행 | DISTRIBUTED(+레거시 null), CALCULATED, 지급보류 제외, 주기 노출 규칙 통과 |
| 7 | 정산보류내역 | 지급 보류(`payout_hold_yn`) 등 별도 보류 축 | 보류 플래그·업무 규칙 |
| 8 | 유통망정산내역 | 조직 단계별 수익 배분 집계 | 가맹점정산내역과 **동일 실행 집합**(DISTRIBUTED 게이트) |
| 9 | 담보금내역 | 롤링·담보 예치/반환 | 담보 원장 |
|10 | 환수금관리 | 정산 후 역발생 회수 | FIFO 차감 순서 상위: 환수 → 미수 |
|11 | 미수금관리 | 미수 채권·차감 | 환수 다음 FIFO |
|12 | 정산리포트 | 집계·실시·집계표·확정 리포트 | **AGG/EXE/SUM**: 가맹점정산내역과 동일 DISTRIBUTED 게이트 + 주기 노출 + 지급보류 제외. **RST**: CALCULATED + DISTRIBUTED + 상세 API 동일 |

## 4. 금액 파이프라인 (직관적 식)

실행 단위(가맹·통화·정산일)에서 대략 다음 순서로 이해합니다. (실제 구현은 `SettlementRun` 저장 필드·정책 유틸과 일치.)

1. **매출**: 승인금액 − 환불/취소 → 순매출(`net`).
2. **거래 수수료**: MDR·건당·기타 (수수료내역과 동일 규칙).
3. **VAT**: 거래 수수료·정산 수수료 등 정책에 따른 부가세 (`feeVat` 등).
4. **담보(롤링)**: `rolling_reserve` — 지급에서 보류되는 금액.
5. **정산 수수료**: 실행당 1회 배치 수수료 (`settlement_batch_fee`).
6. **지급액(송금 전)**: 순매출 − (거래수수료·담보·정산수수료·VAT 정책 반영 등 저장 로직) ± 미수·환수 FIFO 반영 → `pay_amt` (화면 `payAmount`).
7. **송금 수수료**: 이체/USDT 등 실 송금 단계 비용 → **최종 지급액** = 지급액 − 송금수수료 (화면 `finalPayAfterRemittance` 등).

**지급예정일**: 본 시스템에서는 해당 실행의 **정산일(`calc_dt`)** 과 동일하게 표시(메타·안내 참고).

## 5. 중복·통합 권장

- **정산배포 vs 정산대기**: 탭으로 이미 분리되어 있으면 메뉴는 유지해도 무방. 하나의 「정산배포」 화면에서 탭만 전환하는 UX도 가능.
- **통합정산 vs 정산실행**: 역할이 다름(결제 예정 vs 실행 행·수동 트리거).

## 6. 코드 게이트 위치

| 게이트 | 주요 호출부 |
|--------|-------------|
| DISTRIBUTED | `ApiSettlementController#franchiseList`, `#distributionList`, 확정 리포트 목록, `SettlementReportService` AGG/EXE/SUM 루프 |
| 주기 노출 | `isMerchantStatementVisibleSettlementRun` — 위 목록과 리포트 공통 |
| 상세(거래 목록) | 배포·CALCULATED 검증 후 상세 API 허용 |

변경 시 **한 메서드(`SettlementCalcService`)만 수정**하면 가맹 내역·유통·리포트가 함께 맞춰지도록 유지합니다.
